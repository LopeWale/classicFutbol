## Key question 1: For each technique: core formula, tunable parameters, typical values, cost for ~20 agents, known artefacts and standard fixes

### Takeaway
Every production avoidance system in use today is one of three families: (1) force/steering blends (Reynolds, Helbing social force, Karamouzas time-to-collision forces), which are cheap and smooth but can oscillate and can push agents through each other; (2) velocity-space selection with reciprocity (RVO/HRVO/ORCA, and DetourCrowd's sampled RVO), which is collision-free under assumptions but suffers symmetric deadlocks and needs priority/perturbation; and (3) direction-space scoring (context steering), which is deterministic and easy to clamp but is not reciprocal. Production libraries ship with time horizons of 2.5 s (Detour) to 5 to 10 s (RVO2 examples), at most 6 to 10 neighbours, and a post-hoc overlap "push-out" pass, and every one of them exposes a per-agent priority or weight so that some agents yield more than others.

### Cited Findings

**A. Reynolds steering behaviours (seek/arrive/separation/unaligned collision avoidance)**
- Seek is defined by `to_target = target_position - my_position; desired_velocity = normalize(to_target) * max_speed; steering = desired_velocity - velocity` (source) — [Pogamut steering-behaviours lecture slides](https://diana.ms.mff.cuni.cz/pogamut_files/lectures/2015-2016/steeringBehaviors-slides.pdf); the arrival variant "scales the desired speed down by distance to the target" (source) — same slides.
- The per-tick integration loop is `accel = clampLen(accel, maxAccel); velocity = velocity + accel * timeDelta; velocity = clampLen(velocity, maxVelocity)` (source) — [Charles University AI for games, lecture 4](https://ksvi.mff.cuni.cz/~dingle/2025-6/ai_games/lecture_4.pdf); another restatement gives "acceleration = steering_force / mass — truncated by max_force" (source) — [UMD CMSC425 lecture 19](https://www.cs.umd.edu/class/spring2013/cmsc425/Lects/lect19.pdf).
- Separation: "steer away from nearby flockmates, with separation force inversely proportional to distance" (source) — [Charles University lecture 4](https://ksvi.mff.cuni.cz/~dingle/2025-6/ai_games/lecture_4.pdf).
- Unaligned collision avoidance is predictive: "determine the point of nearest approach for each other boid, assume boids continue with their current velocities, and steer to avoid the location of the nearest such potential collision" (source) — [UW CSE457 flocking handout](https://courses.cs.washington.edu/courses/cse457/15sp/projects/animator/flocking.pdf); the original is Reynolds (1999) "Steering Behaviors for Autonomous Characters", GDC 1999 — [PDF mirror at Utrecht University](https://ics-websites.science.uu.nl/docs/vakken/mcrws/papers_new/Reynolds%20-%201999%20-%20Steering%20behaviors%20for%20autonomous%20characters.pdf) (host blocked in this session; the canonical page is red3d.com/cwr/steer/gdc99/).
- The StarCraft II navigation stack is reported (unofficially, in a forum post) to use "six steering forces: following, flocking, grouping, separation, avoidance, and arrival" on top of a constrained-Delaunay navmesh with A* and a funnel filter that accounts for unit radii — [GameDev.net thread on SC2 pathfinding](https://www.gamedev.net/topic/624135-does-starcraft2-use-navmesh-a-or-grid-a-for-pathfinding/); a separate thread quotes Dave Mark that SC2 "uses a navmesh, and there is a bunch of steering code happening in there rather than simple A*" — [GameDev.net thread 563819](https://gamedev.net/forums/topic/563819-whats-starcraft2s-pathfinding-tech/). The official talk is James Anhalt (Blizzard), "AI Navigation: It's Not a Solved Problem - Yet", GDC 2011 AI Summit — [GDC 2011 AI Summit listing](https://hanecci.hatenadiary.org/entry/20101219/1292762130); the slides were reported as a broken zip on the Vault — [GameDev.net](https://www.gamedev.net/topic/624135-does-starcraft2-use-navmesh-a-or-grid-a-for-pathfinding/).

**B. Velocity Obstacles, RVO, ORCA (RVO2 library, van den Berg et al.)**
- The RVO paper claims the framework "is guaranteed to generate safe and oscillation-free motions under the assumption that other agents reason the same way" (source) — [van den Berg et al., RVO, ICRA 2008](https://www.cs.unc.edu/~geom/RVO/icra2008.pdf); the RVO2 project page says the algorithm "ensures that each agent exhibits no oscillatory behaviors" (authors' claim) — [RVO2 library page](https://gamma.cs.unc.edu/RVO2/).
- RVO2 agent parameters and the library's own guidance (source, quoted from the header): `neighborDist` — "The larger this number, the longer the running time of the simulation. If the number is too low, the simulation will not be safe. Must be non-negative."; `maxNeighbors` — "The maximum number of other agents this agent takes into account in the navigation. The larger this number, the longer the running time of the simulation."; `timeHorizon` — "The larger this number, the sooner this agent will respond to the presence of other agents, but the less freedom this agent has in choosing its velocities. Must be positive."; `timeHorizonObst` — same wording for obstacles; `radius`, `maxSpeed` — "Must be non-negative."; time step — "Must be positive." The header says nothing about determinism or agent ordering — [RVO2 `RVOSimulator.h`](https://raw.githubusercontent.com/snape/RVO2/main/src/RVOSimulator.h).
- ORCA half-plane construction per neighbour, from `Agent::computeNewVelocity` (source): `invTimeHorizon = 1/timeHorizon`; `relativePosition = other.pos - pos`; `relativeVelocity = vel - other.vel`; `combinedRadius = r + r_other`. If not already colliding (`distSq > combinedRadiusSq`): `w = relativeVelocity - invTimeHorizon * relativePosition`; if `dot(w, relativePosition) < 0` and `dot^2 > combinedRadiusSq * |w|^2` the velocity projects onto the cut-off circle: `u = (combinedRadius*invTimeHorizon - |w|) * unitW`, `line.direction = (unitW.y, -unitW.x)`; otherwise it projects onto the left or right leg (`leg = sqrt(distSq - combinedRadiusSq)`, side chosen by `det(relativePosition, w) > 0`) with `u = (relativeVelocity . line.direction) * line.direction - relativeVelocity`. If already colliding: `invTimeStep = 1/timeStep`, `w = relativeVelocity - invTimeStep * relativePosition`, `u = (combinedRadius*invTimeStep - |w|) * unitW`. In both cases `line.point = velocity_ + 0.5F * u` (each agent takes half the correction: the "reciprocal" part) — [RVO2 `Agent.cc`](https://raw.githubusercontent.com/snape/RVO2/main/src/Agent.cc).
- ORCA solve (source): `linearProgram2` starts from the preferred velocity clipped to the max-speed disc and, for each violated half-plane, calls `linearProgram1` (1-D intersection of that line with the disc and earlier constraints); if infeasible it returns the failing line index and `linearProgram3` runs, keeping obstacle lines fixed and re-solving a 2-D problem along the perpendicular direction, tracking the largest violation ("distance") so far — the code comments describe this as a fallback for infeasible cases — [RVO2 `Agent.cc`](https://raw.githubusercontent.com/snape/RVO2/main/src/Agent.cc).
- Neighbour selection (source): `computeNeighbors` queries obstacles within `timeHorizonObst*maxSpeed + radius`, then agents within `rangeSq = neighborDist^2`; `insertAgentNeighbor` insertion-sorts by squared distance, keeps at most `maxNeighbors`, and once full sets `rangeSq = agentNeighbors_.back().first` (shrinks the search radius to the farthest kept neighbour). Update is `velocity_ = newVelocity_; position_ += velocity_ * timeStep;` — [RVO2 `Agent.cc`](https://raw.githubusercontent.com/snape/RVO2/main/src/Agent.cc).
- Example parameter sets shipped with RVO2 (typical, in RVO2's abstract units): Circle example: `setTimeStep(0.25)`, `setAgentDefaults(neighborDist=15, maxNeighbors=10, timeHorizon=10, timeHorizonObst=10, radius=1.5, maxSpeed=2.0)`, 250 agents on a circle of radius 200; no perturbation — [RVO2 `examples/Circle.cc`](https://raw.githubusercontent.com/snape/RVO2/main/examples/Circle.cc). Blocks example: `setTimeStep(0.25)`, `setAgentDefaults(15, 10, 5, 5, 2.0, 2.0)`, 100 agents, and the preferred velocity gets a small random perturbation with the comment "Perturb a little to avoid deadlocks due to perfect symmetry." (source) — [RVO2 `examples/Blocks.cc`](https://raw.githubusercontent.com/snape/RVO2/main/examples/Blocks.cc).
- Deadlock literature: ORCA "usually fails to plan reasonable collision avoidance velocities where robots are distributed symmetrically, so the robot gets stuck" — [Robotica, "Addressing the deadlock problem of ORCA in distributed multirobot navigation"](https://www.cambridge.org/core/journals/robotica/article/abs/addressing-the-deadlock-problem-of-the-optimal-reciprocal-collision-avoidance-algorithm-in-distributed-multirobot-navigation/70CEA27CFAE13D30DD3ABCD189F9019D) (the paper tunes an "escape velocity and collision-avoidance responsibility" to reduce deadlocks); Reciprocally-Rotating VOs note that rotation "results in more asymmetry, which is a crucial condition for choosing deadlock-resolving velocities" — [RRVO project page](https://parasollab.web.illinois.edu/research/rrvo/); C-ORCA* observes the usual fallback "is only triggered after a deadlock has already occurred" and instead lets agents wait early — [C-ORCA*, SoCS](https://ojs.aaai.org/index.php/SOCS/article/download/43087/50647/47192); ORCA "may deadlock when polygonal shapes are used, despite being fast and efficient for circular-shaped agents" — [Giese thesis, TAMU 2014](https://oaktrust.library.tamu.edu/bitstream/1969.1/152671/1/GIESE-THESIS-2014.pdf); a 70-agent benchmark reports ORCA producing collisions that a Voronoi-constrained variant avoided — [V-RVO, arXiv 2102.13281](https://arxiv.org/pdf/2102.13281).
- Game adoption: an AiGameDev survey says ORCA/RVO "have seen a sharp rise in adoption ... in particular thanks to titles like CRYSIS 2, SPACE MARINE"; "RESISTANCE 3 uses an RVO-style implementation for collision avoidance" with physics handling walls; Space Marine's RVO library "produces fast avoidance for enemies, though this can lead to large dense clusters at points in the game" (source) — [AiGameDev article hosted by UNC](https://gamma.cs.unc.edu/RVO2/publications/AIGD12.pdf).

**C. Sampled reciprocal avoidance: DetourCrowd (Mikko Mononen's Recast/Detour), the basis of Unreal's Detour Crowd**
- Parameter struct (source): `dtObstacleAvoidanceParams { float velBias; float weightDesVel; float weightCurVel; float weightSide; float weightToi; float horizTime; unsigned char gridSize; unsigned char adaptiveDivs; unsigned char adaptiveRings; unsigned char adaptiveDepth; }`, with `DT_MAX_PATTERN_DIVS = 32` and `DT_MAX_PATTERN_RINGS = 4` — [`DetourObstacleAvoidance.h`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Include/DetourObstacleAvoidance.h).
- Shipped defaults set in `dtCrowd::init` (typical, source code): `velBias = 0.4f; weightDesVel = 2.0f; weightCurVel = 0.75f; weightSide = 0.75f; weightToi = 2.5f; horizTime = 2.5f; gridSize = 33; adaptiveDivs = 7; adaptiveRings = 2; adaptiveDepth = 5;` applied to all `DT_CROWD_MAX_OBSTAVOIDANCE_PARAMS` (= 8) slots — [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp), [`DetourCrowd.h`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Include/DetourCrowd.h).
- Candidate-velocity cost (source): `vpen = weightDesVel * dist(vcand, dvel) * invVmax`; `vcpen = weightCurVel * dist(vcand, vel) * invVmax`; reciprocal relative velocity `vab = 2*vcand - vel - cir->vel` ("assumes both agents take half the avoidance responsibility"); side bias accumulates `clamp(min(dot2D(dp, vab)*0.5 + 0.5, dot2D(np, vab)*2), 0, 1)` per circle then divides by the circle count; time of impact from `sweepCircleCircle` (`c = |s|^2 - r^2, a = |v|^2, b = v.s, d = b^2 - a*c, tmin = (b - sqrt(d))/a`); if already overlapping (`htmin < 0 && htmax > 0`) then `htmin = -htmin * 0.5` "so it avoids more strongly"; wall hits get `htmin *= 2` (less urgent); `tmin` starts at `horizTime` and keeps the smallest; `spen = weightSide * side; tpen = weightToi * (1 / (0.1 + tmin * invHorizTime)); penalty = vpen + vcpen + spen + tpen`, with an early-out when the accumulated penalty already exceeds the best so far — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp).
- Side preference (`prepare()`, source): `dp = normalize(cir->p - pos)`, `dv = cir->dvel - dvel`, `a = dtTriArea2D(orig, dp, dv)`; `np` is `dp` rotated 90 degrees with the rotation sign chosen by `a < 0.01`, which "determines which side the agent should pass on" — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp).
- Adaptive sampling (source): pattern of `1 + nr*nd` points (one at zero, rings of radius `(nr - j)/nr`, points alternating left/right around the desired direction, half-step rotated); start `cr = vmax * (1 - velBias)` and `res = dvel * velBias`; repeat `depth` times: place `res + pattern[i]*cr`, skip candidates faster than `vmax + 0.001`, keep the lowest penalty, set `res = best`, `cr *= 0.5`. Grid sampling: `cs = vmax*2*(1 - velBias)/(gridSize - 1)` over a `gridSize x gridSize` grid centred on `dvel*velBias`, skipping speeds above `vmax + cs/2` — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp).
- Neighbour budget (source): `DT_CROWDAGENT_MAX_NEIGHBOURS = 6` ("The maximum number of neighbors that a crowd agent can take into account for steering decisions"); neighbours are gathered within `collisionQueryRange` ("Defines how close a collision element must be before it is considered for steering behaviors. [Limits: > 0]") and inserted "based on the distance" (sorted ascending); `separationWeight` is documented as "How aggresive the agent manager should be at avoiding collisions with this agent. [Limit: >= 0]"; update flags `DT_CROWD_ANTICIPATE_TURNS=1, DT_CROWD_OBSTACLE_AVOIDANCE=2, DT_CROWD_SEPARATION=4, DT_CROWD_OPTIMIZE_VIS=8, DT_CROWD_OPTIMIZE_TOPO=16` — [`DetourCrowd.h`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Include/DetourCrowd.h), [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp).
- Detour separation force (source): `separationDist = collisionQueryRange; weight = separationWeight * (1 - sqr(dist/separationDist))`, accumulated displacement averaged by neighbour count, then the desired velocity is rescaled if `speedSqr > desiredSpeed^2` — [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp). If `DT_CROWD_OBSTACLE_AVOIDANCE` is not set, `nvel = dvel` (desired velocity used directly) — same file.
- Unreal Engine: "the Detour Crowd Manager handles agent avoidance using an adaptive RVO sampling calculation"; the separate "RVO Avoidance" lives in the Character Movement component and "does not use the navigation mesh"; the docs say the two "work independently, so a project should use one or the other", and a forum answer warns "it's usually not good to have both systems running, as they will start colliding with each other"; the JP docs use `Avoidance Consideration Radius = 100` (cm) as the example value (source) — [UE docs: Using Avoidance With the Navigation System](https://dev.epicgames.com/documentation/unreal-engine/using-avoidance-with-the-navigation-system-in-unreal-engine), [UE forum: Detour crowds vs RVO Avoidance](https://forums.unrealengine.com/t/detour-crowds-vs-rvo-avoidance/313908). `FCrowdAvoidanceConfig` exposes `AdaptiveDivisions` ("number of divisions per ring in adaptive sampling"), `AdaptiveRings`, `AdaptiveDepth`, `DesiredVelocityWeight`, `ImpactTimeWeight`, `ImpactTimeRange` (seconds) — [UE API: FCrowdAvoidanceConfig](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/AIModule/FCrowdAvoidanceConfig), [UE forum: Crowd Manager Avoidance Config](https://forums.unrealengine.com/t/crowd-manager-avoidance-config/315169) (the forum reports 4 config entries by default, one per quality level, all with identical values; "Avoidance Weight is not used by Detour's crowd simulation, but by the RVO in the character movement component").
- Unity NavMeshAgent: `ObstacleAvoidanceType` has five levels — `NoObstacleAvoidance`, `LowQualityObstacleAvoidance` ("simple avoidance, low performance impact"), `MedQualityObstacleAvoidance`, `GoodQualityObstacleAvoidance` ("good avoidance, high performance impact"), `HighQualityObstacleAvoidance` ("highest precision, highest performance impact") (source) — [Unity ObstacleAvoidanceType](https://docs.unity3d.com/2017.4/Documentation/ScriptReference/AI.ObstacleAvoidanceType.html); `obstacleAvoidanceType` trades "the precision of obstacle avoidance against the processor load" — [Unity NavMeshAgent.obstacleAvoidanceType](https://docs.unity3d.com/ScriptReference/NavMeshAgent-obstacleAvoidanceType.html).

**D. Predictive / time-to-collision models (Karamouzas et al.)**
- 2009 predictive model: "Each pedestrian predicts possible future collisions with other pedestrians and then makes an efficient move to avoid them", producing "considerably shorter and less curved paths, ensuring smooth avoidance behaviour" (source) — [Karamouzas, Heil, van Beek, Overmars, Motion in Games 2009, LNCS 5884](https://link.springer.com/doi/10.1007/978-3-642-10347-6_4); a survey describes it as "an evasion force, that depends on the predicted point of collision and the distance to it, is applied to each agent" — [Human Motion Trajectory Prediction: A Survey, arXiv 1905.06113](https://arxiv.org/pdf/1905.06113). The 2010 follow-up is velocity-based — [Karamouzas and Overmars, VRIPHYS 2010](https://diglib.eg.org/handle/10.2312/PE.vriphys.vriphys10.125-134).
- Universal power law (PRL 113, 238701, 2014): the interaction is "based not on the physical separation between pedestrians but on their projected time to a potential future collision"; τ is "the duration of time for which two pedestrians could continue walking at their current velocities before colliding"; `g(τ) ∝ exp[-E(τ)/E0]` so `E(τ) ∝ ln[1/g(τ)]`; the data show "a quadratic falloff as a function of τ"; for τ below about 200 ms the energy "saturates to a maximum value, likely as a consequence of finite human reaction times"; for large τ "the observed interaction energy quickly vanishes, suggesting a truncation of the interaction" (source) — [arXiv 1412.1082 abstract/HTML](https://www.arxiv.org/abs/1412.1082), [APS PRL](https://link.aps.org/doi/10.1103/PhysRevLett.113.238701); Nature's news coverage says "the team's model breaks down if the anticipated time to the next collision is longer than three seconds" — [Nature news](https://www.nature.com/articles/nature.2014.16385).
- Secondary restatements of the model give the potential as `V(τ) = K · exp(-τ/τc) / τ^p` with `p = 2` and `τc = 3.0 s` (source for the restatement; the PRL paper's own constants were not retrievable in this session) — [Time-continuous microscopic pedestrian models: an overview, arXiv 2308.07450](https://arxiv.org/pdf/2308.07450), [arXiv 2211.03419](https://arxiv.org/pdf/2211.03419). The overview notes that "inserting the force that derives from this energy into Newton's equation yields a force-based model" that "accounts for anticipation over an unbounded horizon while using only current positions and velocities".
- The game-developer treatment is Guy and Karamouzas, "Guide to Anticipatory Collision Avoidance", Game AI Pro 2 ch. 19 (pp. 195–208; sections Key Concepts, Prototype Implementation, Advanced Approaches), free download from gameaipro.com — [O'Reilly chapter page](https://www.oreilly.com/library/view/game-ai-pro/9781482254792/K23980_C019.xhtml), [UMN record](https://experts.umn.edu/en/publications/guide-to-anticipatory-collision-avoidance/), [gameaipro.com](https://www.gameaipro.com/); there is also a GDC talk "Force-Based Anticipatory Collision Avoidance" — [GDC Vault](https://gdcvault.com/play/1021986/Forced-Based-Anticipatory-Collision-Avoidance).

**E. Social force model (Helbing and Molnár 1995; Helbing, Farkas, Vicsek 2000)**
- Form (restated in a 2024 AAAI paper): `m_i a_i = f_i,dest + Σ_j f_ji,ped + Σ_o f_oi,env`, with the goal term `f_i,dest = m_i (v_id n_iD - v_i)/τ` where `v_id` is desired speed, `n_iD` the direction to the destination and τ a global relaxation coefficient (source) — [Social Physics Informed Diffusion Model for Crowd Simulation, AAAI 2024 / arXiv 2402.06680](https://arxiv.org/abs/2402.06680).
- Escape-panic parameters (source): mass `m_i = 80 kg` ("an average soccer fan"); contact constants `k = 1.2·10^5 kg s^-2` and `κ = 2.4·10^5 kg m^-1 s^-1` "determine the obstruction effects in cases of physical interactions"; the authors "chose identical values for all pedestrians to minimise the number of parameters"; one quoted result uses `v0 ≈ 0.8 m/s` — [Helbing, Farkas, Vicsek, arXiv cond-mat/0009448 / Nature 407, 487 (2000)](https://arxiv.org/abs/cond-mat/0009448). A Rust crate states its defaults "come from Table 1 of Helbing, Farkas & Vicsek (2000)" — [rustsim-core avoidance.rs](https://docs.rs/rustsim-core/0.0.1/src/rustsim_core/avoidance.rs.html).
- The power-law paper's premise is that distance-based forces (social force) do not match human data as well as time-to-collision based ones — [arXiv 1412.1082](https://www.arxiv.org/abs/1412.1082).

**F. Context steering (Andrew Fray)**

### Inferences
- Cost for ~20 agents (derived from the cited source values; wall-clock numbers are estimates). DetourCrowd adaptive default evaluates `depth × (1 + rings×divs) = 5 × (1 + 2×7) = 75` candidate velocities per agent per update, each tested against at most 6 neighbours, i.e. about 450 circle-sweep tests (one integer sqrt each) per agent and about 9,000 for 20 agents per tick; the grid mode evaluates `33 × 33 = 1,089` candidates per agent. ORCA builds at most `maxNeighbors` half-planes (10 in the RVO2 examples) and `linearProgram2` is O(lines²) in the worst case, i.e. on the order of 100 line intersections per agent, plus a sqrt per leg projection; the `linearProgram3` fallback adds another O(lines²) pass. Reynolds/separation and TTC-force models cost one pass over neighbours (one sqrt per pair). At 20 agents all of these are well under a millisecond on a modern CPU (estimate); the choice should be driven by behaviour and determinism, not CPU.
- The RVO2 and Detour parameter sets are tuned for slow agents (max speed 2 in RVO2 examples; Detour's `horizTime = 2.5 s` was written for walking NPCs). Football closing speeds reach ~18 m/s (two players at 9 m/s head-on), so a 2.5 s horizon would react to players 45 m away; a horizon of 0.6 to 1.2 s (estimate) is the appropriate order of magnitude, and it should scale with relative speed (cite the power-law finding that human interaction energy vanishes beyond about 3 s and saturates below 200 ms as the outer and inner bounds).
- Artefact-to-fix mapping supported by the sources: symmetric deadlock → asymmetry (priority, RRVO-style rotation, RVO2's perturbation, or an id-based deterministic bias); side-flip oscillation → Detour's `weightSide` plus a per-pair side chosen once from the sign of the relative-velocity triangle area (hysteresis); velocity jitter from re-selection every tick → Detour's `weightCurVel` term and `velBias` centring of the sample pattern on the previous/desired velocity (velocity smoothing inside the cost); over-conservatism → shorter horizon, fewer neighbours; dense clusters (the Space Marine observation) → add a separation/comfort-radius term in the velocity stage rather than relying on the push-out pass.
- "Stopped agents are obstacles": in ORCA a stationary agent still absorbs half the correction (it will be pushed); the production answer is Quantum's `AvoidanceType.None` (others avoid it, it avoids nobody) or Detour's per-agent flag. For football this maps directly onto "the player receiving/shielding the ball is an obstacle".

### Inferences
- A football-specific responsibility scheme consistent with the engine primitives above (recommendation, estimate): assign each player an integer priority class each tick: 0 = ball carrier / designated first-to-ball (treated as `AvoidanceType.None`: never deviates, others avoid), 1 = active defender pressing the carrier (avoids only class 0, with a short horizon), 2 = players with a tactical target (full avoidance), 3 = idle/holding shape (yield most). Responsibility share between two interacting players is then `α_ij = p_i/(p_i+p_j)` instead of ORCA's fixed 0.5 (RVO2 hard-codes `0.5F * u`; changing the share is the asymmetric-responsibility generalisation the Robotica paper tunes), and a class-0 agent gets `α = 0`.
- "Avoid only within a time-to-collision horizon" is already how both ORCA (`timeHorizon`) and Detour (`horizTime`, with `tpen = weightToi/(0.1 + tmin/horizTime)`) work; for sports the horizon should be short (0.6 to 1.2 s, estimate) and the comfort radius (0.8 to 1.2 m per the brief) should enter as an inflated radius only in the velocity stage, with the true capsule radius (0.35 to 0.45 m) used in the push-out stage, so that players still brush past each other instead of leaving unrealistic gaps.
- Heading clamp: none of the engine systems clamps heading change per tick inside the avoidance solver; they rely on an acceleration clamp afterwards (Detour `maxAcceleration*dt`). A per-tick heading clamp belongs in the motion-limit stage (Key question 5).

## Key question 3: Deterministic implementation (fixed point, integer sqrt, table trig, ordered neighbours, bounded iteration)

### Takeaway
Lockstep requires bit-identical results on every machine, which rules out platform floats and any iteration order or RNG draw that can differ; both RVO2 and Detour already iterate neighbours in a fixed, distance-sorted order with a hard cap (10 and 6), and both have bounded inner loops, so they can be ported to fixed point. Photon Quantum demonstrates the pattern commercially: a 48.16 fixed-point type with lookup tables for trig and sqrt driving an HRVO-variant avoidance on a deterministic navmesh. The one thing to avoid is ORCA's `linearProgram3` infeasibility fallback and float-style perturbations; a sampled (Detour-style) or TTC-force solver needs only integer sqrt, multiplies and comparisons.

### Cited Findings
- Age of Empires lockstep ("1500 Archers on a 28.8", Terrano and Bettner): rather than sending unit state, "the design runs the same simulation on every machine. Only player commands travel over the network, and the game's outcome depends on every machine computing identical results"; turns were about 200 ms with the simulation divided into frames sized to the slowest machine; a diverged simulation "was flagged as 'out of sync' and the game stopped"; late joining and patch compatibility are hard — [Game Developer article](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond), [Wikipedia: Lockstep protocol](https://Www.Wikipedia.org/wiki/Lockstep_protocol). A later paper summarises that Age of Empires "is capable of synchronizing 1500 game entities and supports up to eight players" — [Deterministic Lockstep in Networked Games (PDF)](https://hdms.bsz-bw.de/files/7107/DeterministicLockstepInNetworkedGamesPaper.pdf). Cross-platform float indeterminism in RTS sync is covered in — [Game Developer: Cross-platform RTS synchronization and floating point indeterminism](https://gamedeveloper.com/programming/cross-platform-rts-synchronization-and-floating-point-indeterminism); developer forums recommend fixed-point math for lockstep — [Unity discussions: floating point determinism](https://discussions.unity.com/t/floating-point-determinism/425250).
- Desync detection practice: compare "a checksum of game state across machines each update", and on mismatch "search for where the states diverged" — [Stardock dev diary: the hunt for the one sync bug](https://www.stardock.com/games/article/339031/dev-diary-the-hunt-for-the-one-sync-bug); "make sure random is called the same number of times for all clients" — [Wesnoth forums](https://forums.wesnoth.org/viewtopic.php?p=318195).
- Photon Quantum: FP uses "16 lower bits ... for the decimal part, 48 for the integral part" (source) — [Quantum FP struct](https://doc-api.photonengine.com/en/quantum/v3/struct_photon_1_1_deterministic_1_1_f_p.html); `FPLut` "is used internally by trigonometric and square root functions", with tables for sin/cos, sqrt, asin, acos, atan, tan, log2, exp — [Quantum FPLut](https://doc-api.photonengine.com/en/quantum/v3/class_photon_1_1_deterministic_1_1_f_p_lut.html); the navmesh is described as deterministic with HRVO avoidance and dynamic avoidance obstacles — [Quantum 2 navigation overview](https://doc.photonengine.com/quantum/v2/manual/navigation/overview).
- Fixed-point building blocks: a Q16.16 type whose square root "uses integer Newton iteration ... Fully deterministic across targets", with the rule that float conversion "must only be used at the system boundary ... never inside the tick loop" — [Go `engine/fixed` package](https://pkg.go.dev/github.com/coreprime/kbot/engine/fixed); a Rust Q16.16 crate "to ensure bit-exact reproducibility across platforms (x86, ARM, WASM)" — [fixed32 crate source](https://docs.rs/crate/fixed32/0.0.20/source/src/lib.rs); a C library explains why floats break lockstep: "fused multiply-add, libm transcendentals, and -ffp-contract differ across compilers and architectures" — [mas-bandwidth/fixed](https://github.com/mas-bandwidth/fixed). An existing Rust ORCA crate computes half-planes with `f32` and float `sqrt`, so it "would not be deterministic across platforms as written" — [raasta rvo.rs](https://docs.rs/crate/raasta/1.0.0/source/src/rvo.rs).
- Ordered, bounded neighbour iteration already present in the reference implementations: RVO2 insertion-sorts neighbours by `distSq`, caps at `maxNeighbors`, and shrinks `rangeSq` to the farthest kept — [RVO2 `Agent.cc`](https://raw.githubusercontent.com/snape/RVO2/main/src/Agent.cc); Detour inserts neighbours "based on the distance" with `DT_CROWDAGENT_MAX_NEIGHBOURS = 6` — [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp), [`DetourCrowd.h`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Include/DetourCrowd.h). Detour's adaptive search is a fixed `depth` × fixed pattern size; its collision resolve is a fixed 4 iterations — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp), [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp).
- Symmetry breaking in RVO2 is a random perturbation of the preferred velocity ("Perturb a little to avoid deadlocks due to perfect symmetry") — [RVO2 `Blocks.cc`](https://raw.githubusercontent.com/snape/RVO2/main/examples/Blocks.cc).

### Inferences
- Number format (derived): the pitch is ~105 m and squared distances reach ~1.1·10^4 m², so Q16.16 (integer range ±32767) overflows on `distSq` unless intermediates are 64-bit; use Q32.32 or Q48.16 state with 64-bit storage and 128-bit (or carefully pre-scaled 64-bit) intermediates for products, or keep positions in Q16.16 metres and compute `distSq` in a 64-bit accumulator. Resolution: Q16.16 gives 1.5·10^-5 m, far below the 0.01 m slop needed; Q48.16 (Quantum's choice) gives the same resolution with no range problem.
- Required primitives for a Detour-style sampled solver: integer multiply/divide, `isqrt64` (Newton or bit-by-bit), one reciprocal per agent (`invVmax`, `invHorizTime`), and integer comparisons; no trig is needed if the sample pattern is precomputed once as fixed-point unit vectors (or built from a 64- or 128-entry sin/cos table). For a TTC-force (power-law) solver you additionally need `exp(-τ/τ0)` from a small LUT. For ORCA you need `isqrt`, divisions, and the LP; the `linearProgram3` fallback is the hardest part to make robust in fixed point (it re-projects lines and divides by near-zero determinants).
- Deterministic tie-breaking: both reference libraries sort by distance only; two neighbours at identical squared distance (common on a symmetric kick-off) would be ordered by insertion order. Sort by `(distSq, agent_id)` and iterate agents in id order so the result is independent of container layout. Replace RVO2's random perturbation with a seeded PRNG drawn in a fixed per-agent order, or better a deterministic bias (e.g. pass on the side given by the sign of `cross(dp, dv)` as Detour does, with ties broken by `agent_id` parity).
- Bounded iteration budget per tick for 22 agents (derived from the Detour defaults): 22 × 75 candidates × 6 neighbours ≈ 10k sweep tests, each one `isqrt64`; trivially within a 60 Hz frame on any target including WASM (estimate).

### Gaps
- No published, open-source fixed-point ORCA/RVO implementation was found; Quantum's avoidance internals are not documented beyond "HRVO variant" and the FP/LUT facts above.
- The exact LUT sizes and interpolation used by Quantum's `FPLut` are not documented in the reachable API pages.

## Key question 4: Post-collision resolution (capsule/circle push-out), push distribution and damping

### Takeaway
Production crowds resolve residual overlap with a position-only relaxation pass that never writes to velocity: DetourCrowd runs 4 iterations, moves each agent half of the penetration scaled by 0.7, averages over its neighbours, and applies the displacement to the position after integration. Rigid-body engines reach the same effect with soft constraints (Box2D v3: contact stiffness 30 Hz, damping ratio 10, push-out speed capped at 3 m/s). The sim's reported 1.25 m/s (p99) position corrections are a symptom of overlap being created upstream; the fix is to make the velocity stage avoid overlap (Detour's "already overlapping → `htmin = -htmin*0.5` → avoid more strongly") and to cap and damp the push-out.

### Cited Findings
- DetourCrowd "Handle collisions" (source): `COLLISION_RESOLVE_FACTOR = 0.7f`; `for (int iter = 0; iter < 4; ++iter)`; for each neighbour, penetration `pen = (r - dist)`, then `pen = (1.0f/dist) * (pen*0.5f) * COLLISION_RESOLVE_FACTOR` (half the overlap times 0.7 along the unit separation direction); accumulated displacements are averaged with `iw = 1.0f / w` where `w` counts contributing neighbours; coincident agents (`dist < 0.0001f`) are separated along a perpendicular to the desired velocity chosen by index order (`idx0 > idx1`) with `pen = 0.01f`; the displacement is applied to `npos` (position), not to `vel` — [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp).
- Detour's velocity stage already penalises existing overlap: when `htmin < 0 && htmax > 0` "the agent is already overlapping. The code sets `htmin = -htmin * 0.5`, so it avoids more strongly" — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp).
- Box2D v3 world defaults (source): `def.contactHertz = 30.0; def.contactDampingRatio = 10.0f; def.contactSpeed = 3.0f * lengthUnits;` (metres per second, the maximum contact push-out speed), `def.restitutionThreshold = 1.0f * lengthUnits; def.maximumLinearSpeed = 400.0f * lengthUnits;` — [Box2D `src/types.c`](https://raw.githubusercontent.com/erincatto/box2d/main/src/types.c). Soft constraints are tuned by a frequency in Hertz and a damping ratio; "below one the system oscillates, and at one the oscillation disappears (critical damping)"; a simple time-stepped integrator "blows up when damping is zero" — [Erin Catto, Soft Constraints, GDC 2011](https://box2d.org/files/ErinCatto_SoftConstraints_GDC2011.pdf), [Avian physics softness docs](https://idanarye.github.io/bevy-tnua/avian2d/dynamics/solver/softness_parameters/index.html). Speculative contacts add constraints for nearly-touching points "to avoid overshoot that causes jitter" — [Drake docs on hydroelastic margin](https://drake.mit.edu/doxygen_cxx/group__hydro__margin.html).
- Soft circle separation in d3-force: nodes are circles pushed apart; "to reduce jitter, this is by default a 'soft' constraint with a configurable strength and iteration count"; the per-iteration correction "is dampened by the force's strength such that the resolution of simultaneous overlaps can be blended together"; "increasing the number of iterations greatly increases the rigidity of the constraint, at higher runtime cost" — [d3-force collide](https://d3js.org/d3-force/collide).
- A game engine's overlap solver with a small `CONTACT_SLOP`, a per-contact correction cap, a fixed number of position iterations, and correction "split by inverse mass, so a heavier body moves less" — [halley-core overlap_physics.rs](https://docs.rs/halley-core/0.3.0/src/halley_core/overlap_physics.rs.html).
- Helbing's physical-contact terms use body-compression `k = 1.2·10^5 kg s^-2` and sliding-friction `κ = 2.4·10^5 kg m^-1 s^-1` for 80 kg pedestrians — [Helbing, Farkas, Vicsek 2000](https://arxiv.org/abs/cond-mat/0009448) (force-based alternative to position projection; not recommended for a 60 Hz game loop, see inferences).

### Inferences
- Why the current p99 of 1.25 m/s is high (estimate): 1.25 m/s at 60 Hz is a 2.1 cm position jump per tick, i.e. roughly a 4 cm overlap resolved fully in one tick between two 0.4 m capsules. The reference systems would instead (a) move each agent only `0.5 × 0.7 = 35%` of the overlap per iteration (Detour), (b) cap the push speed (Box2D 3 m/s default, equivalently 5 cm per tick at 60 Hz, derived), and (c) never add the correction to the velocity state, so the renderer and the next tick's avoidance see a continuous velocity.
- Recommended distribution (estimate, consistent with the inverse-mass split in halley-core and Detour's per-agent `separationWeight`): split each pair's correction by `w_i = (1/m_i) × yield_i` where `yield_i` is 0 for the ball carrier / class-0 agent, so the carrier is never displaced by a teammate, and renormalise so the pair still resolves the full target overlap.
- Recommended damping (estimate): resolve only `overlap - slop` with `slop = 0.5 to 1 cm`; apply a relaxation factor 0.5 to 0.7 per iteration with 2 to 4 iterations in fixed agent-id order; cap per-tick displacement at 2 to 3 cm (≈1.2 to 1.8 m/s at 60 Hz); feed the residual overlap (not the correction) into the next tick's avoidance cost as Detour does via `htmin`.
- Capsules vs circles: in top-down football a player is a vertical capsule, so the 2-D test is circle-vs-circle; the capsule only matters if the sim models slides/dives as horizontal capsules, in which case the segment-circle distance (Detour's `isectRaySeg`/`distancePtSegSqr`) is the primitive.

### Gaps
- No source was found that quantifies acceptable position-correction velocity in a crowd sim; the 3 m/s Box2D value is a rigid-body default, not a crowd-tuned number.
- Erin Catto's Solver2D "Soft Step" write-up itself was not reachable; the soft-constraint facts come from the GDC 2011 slides and Avian's docs.

## Key question 5: Animation coupling: keeping avoidance within turn-rate and acceleration limits

### Takeaway
Every reference pipeline applies avoidance to the *desired* velocity and only then clamps acceleration (Detour: `maxDelta = maxAcceleration * dt`, Reynolds: truncate steering by `max_force` then velocity by `max_speed`), so the motion controller always receives a feasible target; the smoothness comes from penalising deviation from the current velocity inside the avoidance cost (Detour `weightCurVel`, `velBias`) rather than filtering afterwards. Animation-driven studios (IO Interactive's Hitman) go further and let animation capability constrain navigation, and academic work notes most steering algorithms ignore human movement constraints.

### Cited Findings
- Detour's update order (source, from code): compute desired velocity from the path corridor → optional separation modifies `dvel` and rescales to `desiredSpeed` → obstacle avoidance selects `nvel` (or `nvel = dvel` if the flag is off) → `integrate()`: `maxDelta = params.maxAcceleration * dt; if (ds > maxDelta) dv *= maxDelta/ds; vel += dv; npos += vel*dt` → collision resolve on `npos` — [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp).
- Smoothing inside the avoidance cost: `vcpen = weightCurVel * dist(vcand, vel) * invVmax` penalises change from the current velocity (default weight 0.75 vs 2.0 for desired-velocity deviation), and the sample pattern is centred on `dvel * velBias` (default 0.4) — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp), [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp).
- Reynolds' loop truncates the steering force by `max_force` and the velocity by `max_speed` — [UMD lecture 19](https://www.cs.umd.edu/class/spring2013/cmsc425/Lects/lect19.pdf), [Charles University lecture 4](https://ksvi.mff.cuni.cz/~dingle/2025-6/ai_games/lecture_4.pdf).
- ORCA's `timeHorizon` trades reaction time against freedom: "The larger this number, the sooner this agent will respond ... but the less freedom this agent has in choosing its velocities" — [RVO2 `RVOSimulator.h`](https://raw.githubusercontent.com/snape/RVO2/main/src/RVOSimulator.h). The predictive model's selling point is "considerably shorter and less curved paths, ensuring smooth avoidance behaviour" — [Karamouzas et al. 2009](https://link.springer.com/doi/10.1007/978-3-642-10347-6_4).

- Microsoft's avatar-assist patent reduces the steering alteration as the avatar nears the obstacle so that player input dominates close in — [US9421461B2](https://patents.google.com/patent/US9421461B2).

### Inferences
- Pipeline placement (recommendation): avoidance must run on the desired velocity *before* the motion limiter and *before* integration, exactly as Detour does; a heading clamp (max turn rate, e.g. 360 to 720 deg/s at low speed tapering to ~120 deg/s at 9 m/s, estimate) and a speed-dependent acceleration clamp then shape the result into something the locomotion animation can play. Avoidance applied after the limiter (or to position) is what produces sliding.
- Jitter control without lag (recommendation): keep a per-pair "pass side" bit for N ticks (hysteresis), penalise candidates that flip it (Detour `weightSide` analogue), and include Detour's current-velocity penalty; this gives smooth adjustments without a low-pass filter that would add reaction latency.
- Because the push-out pass writes position only, the animation should be driven from the limited velocity (pre-push-out), with the push-out displacement treated as a small root-motion offset blended over several frames (estimate); this is the Detour arrangement and avoids the "sliding" look.

### Gaps
- No reachable source gives numeric turn-rate or acceleration limits used by a sports title's locomotion system; Hitman/2K talks are paywalled or marketing-level.

## Key question 6: Recommended architecture for a 60 Hz deterministic sim (technique, horizon, radii, pipeline order, pseudocode)

### Takeaway
Recommendation: a Detour-style *sampled reciprocal velocity selection* with football priority classes, run in fixed point with a short TTC horizon (~1.0 s), a comfort radius used only in the velocity stage, a strict acceleration/turn-rate limiter afterwards, and a damped, capped, position-only overlap pass last. It needs only integer sqrt and multiplies, has fixed iteration counts, and maps 1:1 onto a tested production design (DetourCrowd / Unreal Detour Crowd), while avoiding ORCA's LP fallback and symmetric deadlocks.

### Cited Findings (the design choices below are grounded in these)
- Sampled RVO with cost terms, side bias, reciprocal `vab = 2*vcand - vel - other.vel`, fixed pattern/depth and overlap handling — [`DetourObstacleAvoidance.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourObstacleAvoidance.cpp); defaults `velBias 0.4, weightDesVel 2.0, weightCurVel 0.75, weightSide 0.75, weightToi 2.5, horizTime 2.5, adaptiveDivs 7, adaptiveRings 2, adaptiveDepth 5` and the update order (desired → separation → avoidance → accel-clamped integrate → 4-iteration push-out at 0.5×0.7) — [`DetourCrowd.cpp`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Source/DetourCrowd.cpp); ≤6 distance-sorted neighbours — [`DetourCrowd.h`](https://raw.githubusercontent.com/recastnavigation/recastnavigation/main/DetourCrowd/Include/DetourCrowd.h).
- ORCA's half-responsibility and its LP fallback — [RVO2 `Agent.cc`](https://raw.githubusercontent.com/snape/RVO2/main/src/Agent.cc); symmetric deadlock and perturbation — [RVO2 `Blocks.cc`](https://raw.githubusercontent.com/snape/RVO2/main/examples/Blocks.cc), [Robotica](https://www.cambridge.org/core/journals/robotica/article/abs/addressing-the-deadlock-problem-of-the-optimal-reciprocal-collision-avoidance-algorithm-in-distributed-multirobot-navigation/70CEA27CFAE13D30DD3ABCD189F9019D).
- Human interaction is governed by time-to-collision with a ~3 s cutoff and ~200 ms saturation — [arXiv 1412.1082](https://www.arxiv.org/abs/1412.1082), [Nature news](https://www.nature.com/articles/nature.2014.16385).
- Priority / "others avoid me" semantics — [Unity avoidancePriority](https://docs.unity3d.com/ScriptReference/AI.NavMeshAgent-avoidancePriority.html), [Quantum AvoidanceType](https://doc-api.photonengine.com/en/quantum/v3/class_quantum_1_1_navigation.html).
- Fixed point with LUT trig/sqrt in a shipping deterministic engine — [Quantum FP](https://doc-api.photonengine.com/en/quantum/v3/struct_photon_1_1_deterministic_1_1_f_p.html), [Quantum FPLut](https://doc-api.photonengine.com/en/quantum/v3/class_photon_1_1_deterministic_1_1_f_p_lut.html); integer Newton sqrt — [Go fixed package](https://pkg.go.dev/github.com/coreprime/kbot/engine/fixed).

### Inferences (the recommendation; all numbers are estimates unless marked)

**Parameters for human-sized players at 0 to 9 m/s (estimates, anchored to the cited defaults):**
- `r_body` = 0.35 to 0.45 m (capsule, from the brief); `r_comfort` = 0.8 to 1.2 m used only in the velocity stage; the overlap pass uses `r_body` only.
- `horizon` = 1.0 s nominal (Detour ships 2.5 s for ~2 m/s walkers; football closing speeds are up to 9× higher, and human data saturate below 0.2 s and vanish above 3 s). Optionally `horizon = clamp(0.6 + 0.04 × |v_rel|, 0.6, 1.5)` s.
- `neighbour_range` = `horizon × (v_max + v_other_max) + 2 r_comfort` ≈ 1.0 × 18 + 2.4 ≈ 20 m, capped at `max_neighbours` = 6 (Detour) to 8, sorted by `(distSq, id)`.
- Candidate sampling: 1 + 2 rings × 8 divisions = 17 samples × 3 depth levels = 51 evaluations per agent (Detour default is 75); start radius `v_max × (1 - velBias)` with `velBias = 0.4`.
- Cost weights (Detour defaults are a good starting point): `w_des = 2.0, w_cur = 0.75, w_side = 0.75, w_toi = 2.5`; add `w_priority` so that a lower-priority agent's `w_des` is scaled down (it gives way) and a class-0 agent skips the solver entirely.
- Motion limits: `a_max(v)` from the existing movement model; turn-rate clamp `θ_max(v)` per tick; apply after avoidance, before integration.
- Push-out: slop 0.01 m, relaxation 0.6, 3 iterations, per-tick cap 0.03 m (= 1.8 m/s at 60 Hz, below the current p99 of 1.25 m/s only if the velocity stage prevents most overlaps; target p99 < 0.3 m/s), weights by `yield_i / m_i`.

**Pipeline order per tick (all loops in ascending agent id; all math in Q48.16 or Q32.32 with 64-bit intermediates):**
1. Tactical layer: target position / role per player (unchanged).
2. Intercept arbitration: elect exactly one "first-to-ball" per team (and the carrier); assign `priority_class` ∈ {0,1,2,3}; class 0 ⇒ `avoid = false`.
3. Desired velocity: `v_des = arrive(target, v_max, slowing_radius)` (Reynolds arrive).
4. Local avoidance (Detour-style sampled RVO with priorities) ⇒ `v_new`.
5. Motion limits: clamp `|v_new - v| ≤ a_max(v)·dt`, clamp heading change ≤ `θ_max(v)·dt`, clamp `|v_new| ≤ v_max`.
6. Integrate: `pos += v_new·dt; v = v_new`.
7. Overlap resolution (position only, damped, capped, priority/mass-weighted); record residual overlap per pair for step 4 next tick.
8. Checksum of positions/velocities for desync detection (lockstep hygiene, per the Stardock/Wesnoth practice cited above).

**Pseudocode (fixed point; `FP` = Q48.16, `mul/div` are 64×64→128 safe, `isqrt` is integer Newton on 64-bit):**

```text
const DT        = FP(1)/60
const HORIZON   = FP(1.0)        // s
const INV_HOR   = FP(1)/HORIZON
const SLOP      = FP(0.01)       // m
const RELAX     = FP(0.6)
const PUSH_CAP  = FP(0.03)       // m per tick
const W_DES=FP(2.0); W_CUR=FP(0.75); W_SIDE=FP(0.75); W_TOI=FP(2.5)
const VEL_BIAS=FP(0.4); RINGS=2; DIVS=8; DEPTH=3
PATTERN[]: precomputed FP unit vectors, 1 + RINGS*DIVS entries,
           ring j radius (RINGS-j)/RINGS, alternating left/right (Detour order)

for i in agents sorted by id:                      // neighbour gather
    N[i] = []
    for j in agents sorted by id, j != i:
        d2 = |p[j]-p[i]|^2
        if d2 < RANGE2: insert (d2, j) into N[i] keeping ascending (d2, j), max 6

for i in agents sorted by id:                      // velocity selection
    if class[i] == 0:  v_new[i] = v_des[i]; continue    // carrier / first-to-ball: never deviates
    rc_i = r_comfort[i]
    // per-neighbour side preference (hysteresis): reuse side[i][j] if set within last 15 ticks
    for (_, j) in N[i]:
        dp = normalize(p[j]-p[i])                   // isqrt
        dv = v_des[j] - v_des[i]
        if side_age[i][j] > 15: side[i][j] = sign(cross(dp, dv)) or (id parity if 0)
        np[j] = rotate90(dp, side[i][j])
    best = +inf; res = v_des[i] * VEL_BIAS; cr = v_max[i] * (1 - VEL_BIAS)
    for depth in 0..DEPTH:
        bvel = res
        for k in 0..len(PATTERN):                   // fixed order, fixed count
            vc = res + PATTERN[k]*cr
            if |vc|^2 > v_max[i]^2: continue
            pen  = W_DES * |vc - v_des[i]| / v_max[i]
            pen += W_CUR * |vc - v[i]|     / v_max[i]
            if pen >= best: continue                // early-out, same as Detour
            tmin = HORIZON; sidesum = 0
            for (_, j) in N[i]:
                share = resp_share(class[i], class[j])          // 1/2 for equals; 1 if j is class 0; 0 never reached here
                vab  = vc + share*(vc - v[i]) ... // simpler: vab = 2*vc - v[i] - v[j] for equal priority (Detour);
                                                 //          vab = vc - v[j]        if j has higher priority (i takes all responsibility)
                s = p[j]-p[i]; R = rc_i + r_comfort[j]
                a = |vab|^2; b = dot(vab, s); c = |s|^2 - R*R
                if a < EPS: continue
                disc = b*b - a*c; if disc < 0: continue
                t0 = (b - isqrt(disc)) / a; t1 = (b + isqrt(disc)) / a
                if t0 < 0 and t1 > 0: t0 = -t0/2                 // already inside comfort disc: avoid harder
                if t0 >= 0 and t0 < tmin: tmin = t0
                sidesum += clamp(min(dot(dp[j],vab)/2 + 1/2, 2*dot(np[j],vab)), 0, 1)
            pen += W_SIDE * sidesum / max(1,len(N[i]))
            pen += W_TOI  / (FP(0.1) + tmin*INV_HOR)
            if pen < best: best = pen; bvel = vc
        res = bvel; cr = cr/2
    v_new[i] = res

for i in agents sorted by id:                      // motion limits + integrate
    dv = v_new[i] - v[i]; if |dv| > a_max(v[i])*DT: dv *= a_max*DT/|dv|
    v_lim = v[i] + dv
    v_lim = clamp_heading_change(v[i], v_lim, theta_max(|v[i]|)*DT)   // table-based angle, or dot/cross test
    v[i] = clamp_len(v_lim, v_max[i]); p[i] += v[i]*DT

for iter in 0..3:                                  // overlap resolution, position only
    disp[*] = 0; cnt[*] = 0
    for i < j (pairs in id order):
        d = p[j]-p[i]; dist = isqrt(|d|^2); R = r_body[i]+r_body[j]
        if dist >= R - SLOP: continue
        if dist < EPS: d = perp(v_des[i]) * (id parity); dist = EPS
        pen = (R - dist - SLOP) * RELAX
        wi = yield[i]/m[i]; wj = yield[j]/m[j]; wsum = wi+wj (if 0: skip)
        disp[i] -= d/dist * pen * wi/wsum; cnt[i]++
        disp[j] += d/dist * pen * wj/wsum; cnt[j]++
    for i: if cnt[i]: step = disp[i]/cnt[i]; p[i] += clamp_len(step, PUSH_CAP)
    // do NOT modify v[i]; record residual overlaps for next tick's cost
```
(`yield[i] = 0` for class 0, 1 otherwise; `resp_share` encodes "teammates yield to higher-priority role"; the carrier is simply excluded from the solver and gets `yield = 0`, so it is never displaced by teammates.)

**Why not ORCA here (inference):** ORCA's `linearProgram3` fallback is where fixed-point implementations become fragile, the fixed 0.5 responsibility must be rewritten for priorities anyway, and the symmetric deadlock is a known failure needing perturbation; the sampled solver has no infeasible case (it always returns the least-bad candidate), degrades gracefully to "slow down" when hemmed in, and its cost is a fixed 51 to 75 evaluations per agent. **Why not pure forces (social force / power law):** they can only push, cannot reason about who passes on which side, and need stiff tuning to prevent overlap at 9 m/s; keep the TTC idea (it is inside `W_TOI/(0.1 + tmin/HORIZON)`) but select velocities rather than integrate forces. **Why not context steering alone:** it is not reciprocal (two context-steering agents each assume the other does nothing), so head-on cases need the reciprocity term that the Detour cost provides.
